# BuilderDocs — Product Vision, Business Workflow & Architecture Guide

## Audit summary (confirmed against the actual schema and API)

The application currently supports the following real data model and workflows without any schema change:

| Form / workflow | Real table(s) | Key fields actually supported | Required vs optional | Notes |
| --- | --- | --- | --- | --- |
| Customers | customers | id, company_id, name, mobile, email, address, city, state, pincode, is_deleted, created_at, updated_at | name required; rest optional unless business validation says otherwise | No GSTIN/PAN storage exists in the reviewed schema. |
| Quotations | documents + document_sections + document_items + document_specifications + document_inclusions + document_exclusions + payment_schedules + document_terms | customer_id, document_number, quotation_date, valid_until, project_name, project_location, project_type_id, floors, builtup_area, area_unit_id, subtotal, additional_charges, discount, tax_name, tax_percentage, cgst/sgst/igst, grand_total, notes | document_number generated by sequence; customer and project info are context-driven | Tax and total fields stay backend-owned; frontend must not re-calculate them independently. |
| Projects | projects | project_number, company_id, customer_id, source_document_id, project_type_id, name, description, site_address, contract_amount, start_date, expected_end_date, actual_end_date, status | name required; customer and contract amount are enforced in the current UI workflow; other dates and details optional | Manual creation is allowed in the current UI, but conversion from accepted quotation remains the preferred flow. |
| Project stages | project_stages | name, sequence_number, planned_start_date, planned_end_date, actual_start_date, actual_end_date, completion_percentage, status | name required | sequence_number is incremental; status uses fixed enum values. |
| Project progress updates | project_progress_updates | title, stage_id, description, progress_percentage, update_date, visibility_status | title required; stage and percentage optional | published/draft visibility is supported. |
| Direct expenses | project_expenses | project_id, category_id, category, description, supplier_name, supplier_bill_number, bill_date, due_date, bill_amount, status, visibility_status | project_id required; category + description + amount required by form validation; supplier invoice fields optional | This is the real direct-cost record. |
| Supplier bills | project_expenses + project_expense_payments | same as direct expenses plus payment records via project_expense_payments | supplier bill fields optional except amount and project | No separate supplier-bill table exists in the reviewed schema; the app distinguishes these only in the UI/workflow. |
| Supplier payments | project_expense_payments | project_expense_id, amount, payment_date, payment_method, reference_number, notes | payment amount and bill reference are required by the model | Status and outstanding balance remain calculated from payment records. |
| Client receipts | project_receipts | project_id, receipt_number, amount, received_date, payment_method, reference_number, notes, visibility_status | project_id + receipt_number + amount required | Receipts remain independent of invoices; no allocation table found. |
| Project attachments | project_attachments | project_id, progress_update_id, expense_id, storage_path, original_filename, mime_type, file_size_bytes, visibility_status | project_id + storage_path + original_filename required | Only implement if the actual upload workflow exists. |
| Project investors | project_investors | project_id, company_id, user_id, name, email, phone, investment_percentage, permissions, is_active | name required; permissions optional booleans | company/project/user IDs are app-managed. |
| Investor contributions | project_investor_contributions | project_investor_id, project_id, company_id, amount, contribution_date, reference_number, notes | amount required | association is constrained to same project/company. |
| Company profile | companies | company_name, address, phone, email, website, gst_number, pan_number, branding fields only if UI supports them | company name required | No ownership IDs or activation fields are intended for the standard profile form. |
| Company settings | company_settings | document prefix, validity days, tax defaults, signatory, bank details | all settings are optional unless the application consumes them | Sensitive bank data should remain grouped and masked. |
| Team management | company_users + users + user_profiles | email, full_name, phone, company_role, is_active | email required in invite flow | no password hash or token fields are shown. |
| Reports | report queries | filters by project/date/status/expense category | filters optional unless required by the report | Export is supported only where report service implements it. |
| Subscription billing | company_subscriptions + company_quotation_usage + subscription_payments | plan, billing_cycle, status, current_period_end, usage counters, payment lifecycle | backend-managed | UI should not allow direct edits to Razorpay IDs or usage counters. |

## Final field specification to keep

### Customers
- Customer Name — required
- Mobile Number — optional
- Email Address — optional
- Address — optional
- City — optional
- State — optional
- PIN Code — optional
- Group address fields under an Address Details section.
- Do not expose soft-delete or auth metadata.

### Quotations
- Quotation Number — generated by existing numbering
- Customer — select existing customer
- Quotation Date — default as allowed by current app
- Valid Until — prefilled from company default where supported
- Project / Work Name, Site Location, Project Type, Floors, Built-up Area, Area Unit
- Repeatable sections and items with section name, description, quantity, unit, rate, line amount
- Subtotal, additional charges, discount, tax name/rate, CGST/SGST/IGST, tax amount, grand total
- Specifications, inclusions, exclusions, payment schedule, terms, notes
- Keep booking-receipt fields in the booking receipt flow, not every quotation form

### Projects
- Project Name — required
- Customer — supported existing flow
- Description, Site Address, Project Type, Contract Amount, Start Date, Expected Completion Date, Status — optional unless current validation requires them
- Project Number and source quotation association are application-managed

### Expenses and Supplier Bills
- Keep one underlying financial record: project_expenses
- Distinguish Direct Expense vs Supplier Bill in the user workflow only
- Fields: project, category, description, amount, supplier/payee, bill number, bill date, due date, notes
- Payment status remains derived from payment records; do not add a manual paid flag

### Supplier Payments
- Select a valid project expense or supplier bill
- Payment Amount, Date, Method, Reference Number, Notes
- Show outstanding balance and previous payments when available

### Client Receipts
- Project, Receipt Number, Amount Received, Date, Payment Method, Reference Number, Notes, Visibility

## Safety constraints

- No schema migration or database change was required for this task.
- No API contract change was required for this task.
- No financial calculation or payment-allocation logic was altered.
- Supplier bills remain represented by the same existing project_expense record unless a backend redesign is explicitly approved.

## Implementation status

- Audit complete against the real codebase and database schema.
- Safe UI-only improvements are applied to the forms that were inconsistent with the schema or unclear in workflow.
- Large backend or database changes are intentionally deferred until explicit approval.
